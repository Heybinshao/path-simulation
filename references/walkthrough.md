# 真实走查范例

> 一次完整的路径模拟长什么样？本文件用两个真实案例回答：
> - **主案例**：path-simulation 测自己（2026-08-06 真实发生），展示**完整闭环**——选路径 → 走查 → 报告 → 使用者确认 → 修复 → 重走 → 停止。
> - **附加案例**：book-distiller v1.1.0 走查，展示**报告态**——被测对象是 user-owned 时，路径模拟只报告、不自动修，等使用者授权。
>
> 两个案例都是真实走查输出，不是虚构演示；「问题」是实打实从文件比对里走出来的。

## 主案例：完整闭环（path-simulation 测自己）

### 测试对象
path-simulation（v2.3.1 时代，含 SKILL.md + references/ 多文件）

### 覆盖路径
标准 / 异常 #6 / 跨文件 #7（多参考文件 → 按步骤 8 强制走 #7）

### 走查轨迹
- **标准路径**：以用户指令「帮我用路径模拟检查 binshao-illustrations」走完整 8 步。步骤 1-8 主干可读、无断链；步骤 4/5「先报告不自动修」自洽。→ 主干无阻断。
- **异常路径 #6**：用户指令改为「走查 /xxx/不存在.md」。走到步骤 1「选一条用户指令作为入口」即卡——skill 全程假设被测对象已存在且有效，**未定义「入口文件/路径无效」时 walker 怎么办**。→ 记问题 #3。
- **跨文件 #7**：逐一比对 SKILL.md 与 4 个 references 对同一概念的措辞。发现 3 处口径漂移 → 记 #1、#2、#4。

### 问题清单（按爆炸半径排序）
| # | 路径 | 问题 | 严重度 | 哪步卡 | 为什么 | 建议修复 |
|---|------|------|--------|--------|--------|---------|
| 3 | 异常 #6 | 被测对象无效/不存在时无处理指引 | 一般 | 步骤 1 | 方法假设入口恒有效，缺异常兜底 | 步骤 1 加一句：入口文件/路径不存在 → 提示重选，不进入走查 |
| 1 | 跨文件 #7 | 坑表/FAQ 未同步新选路口径 | 一般 | 坑表、faq | 主流程已改「标准+风险路径」，但坑表修法仍写「换入口再走」「至少3条」，FAQ Q1 未提风险路径 | 坑表两处 + FAQ Q1 补「须含标准+至少1条风险路径」 |
| 2 | 跨文件 #7 | 坑表#「报告粒度不定」描述停在 v2.3.0 旧模板 | 一般 | 坑表 | 未提本轮新增的严重度列/走查轨迹 | 该条描述补「v2.3.x 起含严重度+走查轨迹」 |
| 4 | 跨文件 #7 | walkthrough.md 为虚构范例未标注 | 建议 | walkthrough.md | 落盘虚构案例，读者可能当真 | 顶部加「虚构演示，建议拿真实 skill 替换」 |

> 严重度：阻断 > 一般 > 建议。本条无阻断，最高为一般。

### 使用者决定
「全修」

### 修复
- #1、#2：SKILL.md 坑表两处 + faq.md 同步「标准+风险路径」口径
- #3：SKILL.md 步骤 1 加「入口无效 → 提示重选，不进入走查」兜底
- #4：walkthrough.md 顶部加虚构标注（后随本文件改为真实案例）

### 重走（验证修复，换路径）
- 标准 ✅ / 异常 ✅ / 跨文件 ✅
- 新路径（跨文件再走一次）→ **无新问题** → 停止

### 闭环结论
4 条全修，重走通过，无新问题 → **达到停止标准**。

**这半段最容易被忽略**：报告不是终点，「修复 → 重走 → 确认无新问题」才是闭环。只报告不闭环，路径模拟就退化成「查一次」而不是「修好一次」。

## 附加案例：被测对象是 user-owned 时停在报告态（book-distiller v1.1.0）

### 为什么这个案例停在报告
book-distiller 是彬少自己的 user-owned skill。路径模拟的纪律是：**发现问题只报告，不自动修**——直接修 = 替作者做设计决定。所以这里走完报告后停在「使用者决定」，等授权才进入修复。

### 测试对象
book-distiller v1.1.0（多参考文件：references/ + templates/ + scripts/）

### 覆盖路径
标准 / 异常 #6 / 跨文件 #7

### 走查轨迹
- **标准路径**：用户「拆解《思考快与慢》epub」。从「环境检测 → 开始前确认 → 源命名检查 → Step1 转换 → 3 个 CHECKPOINT → Step2 提取 → Step3 写入 → Step4 质检 → Step5 移动」走完全程。主干有 CHECKPOINT 钉死、覆盖检查有「绝不自动副本」铁律，无断链 → 主干无阻断。但发现「路径处理说明与 config 不一致」→ 记问题 #1。
- **异常路径 #6**：用户给 `.mobi` 文件。走到 Step1「其他格式」段 → 查到 mobi 需 calibre 先转 epub，且写「未装 calibre 时提示用户，不静默失败」。兜底清晰 → 不卡。但发现 opencc 段只说「繁体时需手动安装」未定义流程动作 → 记问题 #3。
- **跨文件 #7**：逐一比对 SKILL.md ↔ config.json ↔ references 段。发现示例目录名三处不完全对齐、参考文件职责重叠、示意路径未标注真实来源 → 记 #1、#2、#4。

### 问题清单（按爆炸半径排序）
| # | 路径 | 问题 | 严重度 | 哪步卡 | 为什么 | 建议修复 |
|---|------|------|--------|--------|--------|---------|
| 1 | 跨文件 #7 | 「文件名对齐」示例与 config.json 子目录命名不一致 | 一般 | SKILL.md 示例段 vs config.json | 示例冒出 `01-书籍｜epub` 第三目录，且默认路径段写「知识库 01｜收集箱/书籍拆解」而真实 config 是「宝藏彬少｜00｜知识库/01｜收集箱/书籍拆解」——三处不完全对齐 | 统一示例目录名为 config 实际键名；说明示意值非真实值 |
| 2 | 跨文件 #7 | 同名参考文件职责重叠未注优先级 | 一般 | 参考文件段 | `extraction-framework.md` 与 Step2 提取逻辑重叠，未说明以谁为准 | 参考文件段补：「extraction-framework 是 Step2 的概念识别依据，以本文件 Step2 为准」 |
| 3 | 异常 #6 | 繁体书 + opencc 未装时缺明确兜底动作 | 一般 | Step1 环境检测 opencc 段 | 仅说「需手动安装」，未定义流程如何继续 | 补：「未装且遇繁体书 → 提示安装或跳过简转、保留繁体继续」 |
| 4 | 跨文件 #7 | 默认路径示意值 vs 真实 config 值未标注 | 建议 | SKILL.md 默认路径段 | 新用户易误以为路径固定为示意值 | 「当前：」改「示意：」，加「真实路径以 config.json 为准」 |

> 严重度：阻断 > 一般 > 建议。本 skill 成熟，无阻断级，最高为一般。

### 使用者决定
<book-distiller 为 user-owned skill，按步骤 5 不自动修复；报告交付彬少，由其决定是否采纳 #1–#4>

### 结论
通过（无主干阻断）。4 条均为文档一致性 / 边界指引问题——证明「标准 + 风险路径优先 + 跨文件强制」在成熟 skill 上仍能挖出标准路径抓不到的问题。修复与否、何时修复，由所有者决定。

## 两个案例对照：什么时候能闭环，什么时候停在报告

| 被测对象 | 能自动进入闭环吗 | 为什么 |
|---------|----------------|--------|
| 自己的 skill（path-simulation 测自己） | ✅ 报告后使用者确认「全修」→ 修复 → 重走 → 停止 | 修改权在自己手里，确认即授权 |
| user-owned / 第三方 / 共享 skill（book-distiller） | ⛔ 停在报告态 | 直接修 = 替作者做设计决定；只报告、等使用者授权 |
| 官方 skill | ⛔ 停在报告态 | 同 user-owned，且改官方 skill 风险更高，默认不写入 |

**一句话**：报告永远是第一步；能否闭环取决于「你有没有修改权 + 使用者是否确认」。有 → 推完整闭环；没有 → 停在报告，把决定权交还所有者。
