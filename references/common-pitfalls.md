# path-simulation 常见坑（实测沉淀）

## 坑：多轮修订型文档「修订记录与执行块脱节」（2026-08-28 实测）

**被测对象特征**：经过多轮修订的 plan/skill/方案文档，修订历史以「文末追加修订记录（v4.1、v4.2…）」方式演进，正文 Task 执行块是最初版本。

**症状**：顺读正文一切通顺；但把「每条修订记录声称的修正」与「对应执行块的实际内容」逐一比对时，发现执行块还停留在被否掉的旧口径。一轮走查抓出 7 个问题，全部源于同一根因。

**走查手法**：对此类文档，除正常按路径走查外，必须加一个专门步骤——**逐条核对「修订记录声称的修正」在「执行块里是否真的落了」**：

1. 从最早修订节开始，提取每条「声称改了 X」
2. 到对应执行块（Task/步骤/模板）grep 关键新措辞，验证真的改了
3. 同时反向查旧措辞残留（旧口径关键词还在执行区 = 未同步）

**判定**：修订记录说 A、执行块写 B = 阻断级问题。

**修复验证**：修完用脚本断言（grep 新措辞命中数 + 旧措辞在执行区归零）而不是人工顺读——人工顺读正是漏掉它的原因。

## 坑：计划文档的范围边界 = 走查的对象边界（2026-08-28 第二次实测）

**症状**：方案逐节体检看似完备，但落地后用户在「方案没铺到的子区域」连续发现真实问题——方案排查范围默认等于「正在改的那些文件」，而结构类方案的影响面是**整个目录子树**。

**走查手法**：结构类方案走查，在正常路径外加「**子目录盘点路径**」——被方案提及或隐含影响的每个子目录，逐文件问：①内容性质与文件定位还匹配吗 ②有没有被新口径架空的旧方法论/旧写死 ③目录地图/索引有没有把这文件列上。

**判定**：用户替你跑出来的发现 = 方案排查边界画小了，属「一般」级。

**预防（写给写方案的人）**：结构性方案的「排查范围」必须写到子目录粒度并列出每个子目录的处理决定（体检/跳过+理由）。

## 坑：报告基于的旧印象 vs 磁盘真实状态——patch 匹配失败即信号（2026-08-28 第三次实测）

**症状**：走查报告列出「口径矛盾」，修复时照报告旧文本写 old_string，匹配失败——磁盘早已是修正后口径（同会话早前某轮已改过）。

**走查手法**：报告里每条问题，修复动手前先 grep 磁盘确认**现在**是否仍存在；被测对象在本会话内被改过时尤其必查。

**预防（写给走查的人）**：走查中若对被测对象做过任何 patch，出报告前对涉及同文件的问题条目重 grep 一次，报告只报当前成立的问题。

## 坑：并发会话抢改被测对象——走查报告快照过期（2026-08-28 第四次实测，ob-to-html 走查）

**症状**：走查报告列出 7 个问题，使用者说「修」后动手，发现 P1/P2 级一半**已被修好**——另一个并发 Hermes 会话在走查期间改了同一批文件（structure.py 加了单 h1 边界修复、test.py 从 17 用例扩到 29、SKILL.md 升 v3.3.0），系统弹「file was modified by sibling subagent」警告。照报告盲修 = 重复改、或把对方修复当旧口径改回去、或漏掉对方留下的对账项。

**走查手法**：
1. 修复动手前，对报告每条问题先 grep 磁盘确认「现在还成立吗」
2. 见 sibling-modified 警告必须重读该文件再动
3. 发现某条已被修好 → 核实实现质量（方向对不对/实现干不干净/带没带回归用例），干净就采纳并在汇报里注明「已由并发会话修复，我核实保留」——不重复改、不抹对方的注释与用例
4. 对方修了实现但没做文档对账（声称/条数/版本号过期）→ 补对账，这是并发分工里最容易漏的尾巴

**判定**：用户并发开会话是常态。报告 = 某时刻快照，修复 = 现场作业，中间必须重对盘。「发现于走查时」≠「修复时仍成立」的并发版。

**预防（写给走查的人）**：报告里每条问题标注「基于 HH:MM 快照」；出报告与「修」之间隔了较久、或被测对象是用户可能同时在折腾的热文件的，修复前整表重验一遍（每条一行 grep 的事）。

## 坑：模拟器报「硬伤」未复核断言本身——测试代码也会错（2026-09-05 实测，book-distiller 走查）

**症状**：模拟报告 2 项「硬伤」，逐条核实后全是测试断言自己写错——用全角「（」去匹配文件里的半角「(」；忘了模拟调用侧剥扩展名的行为，把正常输出误判为失败。

**走查手法**：报硬伤前先复核断言，三查——①断言用的字符与被测内容编码/全半角一致吗？②被测函数的前提条件（调用侧行为）模拟了吗？③「失败」是内容错还是断言错？负例测试（故意喂坏输入）的断言同样要复核。

**判定**：断言错误 = 误报，不是被测对象的问题；误报进问题清单会浪费使用者确认时间，还会掩盖真问题。

## 坑：正则/启发式类体检的初报直接当结论（2026-09-05 同轮实测）

**症状**：孤儿文件检测初报 7 个孤儿，人工复核全是误报——正则只匹配完整路径格式，没覆盖「汇总行」变体（`scripts/ — a.py / b.py / c.py` 一行列多个文件）。

**走查手法**：正则/启发式类检测的初报必须人工二次核实再定性，尤其格式变体（汇总行、内联引用、别名）。初报当线索，不当结论。

**判定**：检测器盲区 = 误报，修的是检测器不是被测对象；但「初报→复核→定性」一步不能省，否则误报会顶掉真问题。

## 坑：修复的授权以轮次为单位，不延续到同会话后续发现（2026-09-05 实测，自指走查）

**症状**：使用者拍板「迭代 skill」＝授权了方向（v2.7.0 加步骤 0/负例/回归）；执行者在同会话后续自检时发现新问题（坑表行加错位置、格式不匹配），**跳过报告直接修**——事后复盘，违反了两层纪律：①迭代内容本身先斩后奏，执行细节未经确认；②自检发现的问题没走「报告→确认→修复」，直接动手。

**根因**：把「使用者拍板过大方向」错误外推为「同会话内一切后续修复都已授权」。授权是按轮次结算的：每轮走查的新发现，都是一轮新的「报告→确认」。

**走查手法**：同会话内对同一被测对象的多轮走查，每一轮发现的问题**仍然走完整程序**——报告清单→等确认→再修。判断标准：这个问题的修复动作，使用者拍板过吗？没拍板过 = 新一轮报告。

**预防（写给执行的人）**：效率话术（「改动机械」「刚拍板过方向」「都是我自己写的行」）不构成跳过程序的理由。恰恰是「自己刚写的行」最容易出格式/落位错——本轮实际后果：坑表行加错文件 + 格式与既有风格不符，全靠重走才抓出来。

## 坑：机械子串匹配对账人工缩略语，批量报假不符（2026-09-12 实测，xiaobai-longform-style 验收）

**症状**：验证语料索引里 ID→缩略括注（「IP 配图」）与真实标题（「我把“个人 IP 自动配图”做成了开源 Skill：…」）对账，断言用 `括注[:4] in 标题` 子串匹配，6/16 条报「不符」——复核全是假硬伤：缩略是人工语义概括，不保证是原文连续子串。

**根因**：把「缩略语」当「原文片段」验证。[:4] 截首字更碎：「封面 Skill」截「封面」命中的是另一篇「好教程，封面先讲清楚」——就算碰巧通过也是错的口径。

**走查手法**：凡「人工概括/缩略/别名 vs 源文本」对账（括注、备注、索引条目），不做子串机械匹配——提取全部待对项连同真实源文本一次输出，逐条语义核对；子串匹配只适用于逐字引用的回验。断言批量报错（本次 6/16）本身就是断言口径错误的强信号，先查断言再定问题数。

## 坑：「增量验收」的范围声明把必走的 #7 整体豁免掉（2026-09-16 实测，memory-file-maintenance 第四轮验收 vs 同日全量深读）

**症状**：同一 skill、同一天，第四轮验收（范围=本轮 v5.8.1→v5.9.0 变更）走完 P-1~P-4 全绿收工；同日另一会话做全量深读，抓出 3 处跨文件判据打架（SKILL.md 禁用 file_size 口径、某 references 教用该口径；USER.md Binary 误判范围两说；P0/P2 旧分级残留 deep 文件）。走查轨迹里**没有一条跨文件路径**——步骤 8「多参考文件停止前必须至少走一次 #7」被「增量验收」的范围声明整体短路了。

**根因**：#7 原执行定义只有一句「检查参考文件之间是否矛盾」，没定义怎么查（v2.7.2 已在 path-types.md 补「判据配对」执行定义，SKILL.md 步骤 8 与参考清单已挂指针）；增量轮的执行者顺理成章认为「审的是本轮变更，本轮没动 references 就不用走 #7」——旧口径躺在历史文件里，本轮变更集外，扫不到。与「旧短路分支旁路新增强步骤」同族病。

**走查手法**：范围分级只豁免**对变更集的验证深度**，不豁免必走路径类型——凡被测对象含多参考文件，增量轮 #7 仍要走（对象可以是「本轮新口径 vs 全目录存量判据」的配对，成本可控）。

**判定**：「N 轮验收全绿」不等于「跨文件一致」——报告未显式记录 #7 轨迹的，视为 #7 未跑，补走或标注。
